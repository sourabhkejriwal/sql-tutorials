Example 1: Impact of Indexing

Scenario: Find all sales for a specific customer.

Without Index (Slow)

SELECT *
FROM sales
WHERE customer_id = 7001;

Performance

⏱️ Execution Time: 4.5 seconds
📊 Rows Scanned: 5,000,000 rows
🔍 Method: Full Table Scan

With Index (Fast)

-- Create index first
CREATE INDEX idx_customer_id ON sales(customer_id);

-- Same query, now fast!
SELECT *
FROM sales
WHERE customer_id = 7001;

Performance

⏱️ Execution Time: 0.02 seconds
📊 Rows Scanned: 12 rows
🔍 Method: Index Seek
⚡ 225x FASTER!

Example 2: Composite Indexes

Scenario: Find sales by store and date range (common retail query).

-- Inefficient: Two separate indexes
CREATE INDEX idx_store ON sales(store_id);

CREATE INDEX idx_date ON sales(transaction_date);

-- Efficient: Composite index
CREATE INDEX idx_store_date ON sales(store_id, transaction_date);

Composite Index Order Matters!

• Index on (store_id, transaction_date) works for:
✅ WHERE store_id = 101
✅ WHERE store_id = 101 AND transaction_date = '2024-01-15'
❌ WHERE transaction_date = '2024-01-15' (doesn't use index efficiently)

Rule: Put the most selective column first!

Query Performance

SELECT SUM(amount)
FROM sales
WHERE store_id = 101 AND transaction_date BETWEEN '2024-01-01' AND '2024-01-31';

When to Create Indexes

✅ Columns frequently used in WHERE clauses
✅ Columns used in JOIN conditions
✅ Columns used in ORDER BY
✅ Foreign key columns

⚠️ When NOT to Index:
❌ Small tables (< 1000 rows)
❌ Columns with low selectivity (e.g., boolean fields)
❌ Tables with frequent INSERT/UPDATE/DELETE (indexes slow writes)
❌ Columns rarely used in queries

Common Interview Question

"How would you optimize a slow query in our sales database?"
Answer: "First, I'd use EXPLAIN/EXPLAIN ANALYZE to identify if it's doing a full table scan. If the query filters on specific columns like store_id or transaction_date, I'd check if appropriate indexes exist. For queries filtering on multiple columns, I'd consider composite indexes. I'd also look at query execution plans to see if indexes are actually being used."

Technique 1: Use SELECT Specific Columns (Not SELECT *)

Bad Practice

-- Returns ALL 15 columns
SELECT *
FROM sales
WHERE store_id = 101;

Problems

• Transfers unnecessary data over network
• Uses more memory
• Slower performance
• Can't use covering indexes

Best Practice

-- Only get what you need
SELECT sale_id, transaction_date, amount
FROM sales
WHERE store_id = 101;

Benefits

• 70% less data transferred
• Can use covering index
• Faster execution
• More maintainable code

Real Impact on 100,000 rows

SELECT * → 450MB data, 2.1 seconds
SELECT 3 columns → 135MB data, 0.6 seconds
⚡ 3.5x FASTER!

Technique 2: Avoid Functions on Indexed Columns

Index Can't Be Used

-- Function on indexed column prevents index use!
SELECT *
FROM sales
WHERE YEAR(transaction_date) = 2024;

-- Another example
SELECT *
FROM products
WHERE UPPER(product_name) = 'MILK 2L';
⏱️ Time: 3.8 seconds
📊 Rows Scanned: 5,000,000 (Full Scan)

Index Can Be Used

-- Use date range instead
SELECT *
FROM sales
WHERE transaction_date >= '2024-01-01'
    AND transaction_date < '2025-01-01';

-- Store uppercase version or use case-insensitive collation
SELECT *
FROM products
WHERE product_name = 'Milk 2L';
⏱️ Time: 0.08 seconds
📊 Rows Scanned: 425,000 (Index Seek)

Technique 3: Use EXISTS Instead of IN with Subqueries

Scenario

Find all products that have been sold in the last month

Slower: IN with Subquery

SELECT product_name
FROM products
WHERE product_id IN (
    SELECT DISTINCT product_id
    FROM sales
    WHERE transaction_date >= '2024-01-01'
);
⏱️ Time: 1.2 seconds
Problem: Creates large IN list

Faster: EXISTS

SELECT product_name
FROM products p
WHERE EXISTS (
    SELECT 1
    FROM sales s
    WHERE s.product_id = p.product_id
        AND s.transaction_date >= '2024-01-01'
);
⏱️ Time: 0.3 seconds
⚡ 4x FASTER!
Stops searching after first match

When to Use Each

• EXISTS: When checking for existence (recommended for large datasets)
• IN: When you have a small, fixed list of values: WHERE category IN ('Dairy', 'Bakery')
• JOIN: When you need columns from both tables

Technique 4: Limit Results When Possible

Returns Everything

-- Gets ALL sales, even if you only need recent ones
SELECT *
FROM sales
ORDER BY transaction_date DESC;

Use LIMIT/TOP

-- Only get what you need
SELECT *
FROM sales
ORDER BY transaction_date DESC
LIMIT 100;

-- SQL Server syntax

Interview Question

"A dashboard query is taking 30 seconds to load. How would you optimize it?"
Strong Answer: "I'd start by examining the query execution plan. Common issues I'd check: 1) Is it selecting unnecessary columns (SELECT *)? 2) Are there missing indexes on filter/join columns? 3) Are functions being applied to indexed columns? 4) Can we add LIMIT if we're showing paginated results? 5) Are there implicit type conversions? I'd also check if the query can be simplified - sometimes complex CTEs can be rewritten as simpler JOINs."

Optimization 1: Join Order Matters

Scenario

Get product sales data with store information
Table Sizes: sales (5M rows), products (50K rows), stores (500 rows)

Inefficient Join Order

-- Joins largest tables first
SELECT s.sale_id, p.product_name, st.store_name
FROM sales s
JOIN products p ON s.product_id = p.product_id
JOIN stores st ON s.store_id = st.store_id
WHERE st.city = 'Sydney' AND s.transaction_date = '2024-01-15';
Problem: Joins 5M rows with 50K rows first, then filters

Filter First, Join Later

-- Filter before joining
SELECT s.sale_id, p.product_name, st.store_name
FROM sales s
JOIN stores st ON s.store_id = st.store_id AND st.city = 'Sydney' -- Filter in JOIN
JOIN products p ON s.product_id = p.product_id
WHERE s.transaction_date = '2024-01-15';
Better: Reduces dataset early in execution

Optimization 2: Use Appropriate JOIN Types

Wrong JOIN Type

-- LEFT JOIN when INNER JOIN is appropriate
SELECT s.sale_id, p.product_name
FROM sales s
LEFT JOIN products p ON s.product_id = p.product_id;
If every sale MUST have a product, use INNER JOIN

Correct JOIN Type

-- INNER JOIN is more efficient
SELECT s.sale_id, p.product_name
FROM sales s
INNER JOIN products p ON s.product_id = p.product_id;
INNER JOIN is faster - database knows all rows must match

Optimization 3: Avoid Joining on Calculated Fields

Join on Calculation

SELECT *
FROM sales s
JOIN products p ON CAST(s.product_id AS VARCHAR) = p.product_code;

Join on Indexed Columns

-- Ensure data types match, create computed column if needed
ALTER TABLE products ADD product_id_int AS CAST(product_code AS INT) PERSISTED;

CREATE INDEX idx_product_id_int ON products(product_id_int);

SELECT *
FROM sales s
JOIN products p ON s.product_id = p.product_id_int;

Mistake 1: N+1 Query Problem

Bad: Multiple Queries

-- First query: Get all stores
SELECT store_id, store_name
FROM stores;

-- Then for EACH store, run another query (N times!)
SELECT SUM(amount)
FROM sales
WHERE store_id = 101;

SELECT SUM(amount)
FROM sales
WHERE store_id = 102; -- ... repeat 500 times!
Result: 501 queries (1 + 500)
Time: 15 seconds

Good: Single Query with JOIN

SELECT st.store_id, st.store_name, SUM(s.amount) AS total_sales
FROM stores st
LEFT JOIN sales s ON st.store_id = s.store_id
GROUP BY st.store_id, st.store_name;
Result: 1 query
Time: 0.3 seconds
⚡ 50x FASTER!

Mistake 2: Using OR Instead of IN

Inefficient

SELECT *
FROM products
WHERE category = 'Dairy' OR category = 'Bakery'
    OR category = 'Produce' OR category = 'Meat';

Efficient

SELECT *
FROM products
WHERE category IN ('Dairy', 'Bakery', 'Produce', 'Meat');

Mistake 3: Using DISTINCT to Fix Duplicates

Treating Symptoms, Not Cause

-- Using DISTINCT because of duplicate rows
SELECT DISTINCT p.product_name, s.amount
FROM products p
JOIN sales s ON p.product_id = s.product_id;
Problem: DISTINCT is expensive and masks the real issue

Fix the Root Cause

-- Understand WHY there are duplicates
-- Option 1: Aggregate if needed
SELECT p.product_name, SUM(s.amount) AS total_amount
FROM products p
JOIN sales s ON p.product_id = s.product_id
GROUP BY p.product_name;

-- Option 2: Check for data quality issues
-- Option 3: Use proper WHERE conditions

Mistake 4: Implicit Type Conversions

Prevents Index Use

-- store_id is INT, but comparing to VARCHAR
SELECT *
FROM sales
WHERE store_id = '101'; -- String!
Database converts EVERY store_id to VARCHAR
Index can't be used!

Matching Data Types

SELECT *
FROM sales
WHERE store_id = 101; -- Integer!
Index is used efficiently

Interview Scenario

"We have a query that was fast last month but is now slow. What could cause this?"
Answer: "Several possibilities: 1) Data growth - table has grown significantly, indexes may need rebuilding or new indexes needed. 2) Statistics outdated - query optimizer uses old statistics, needs UPDATE STATISTICS. 3) Index fragmentation - indexes need rebuilding. 4) Plan cache issues - old execution plan is being reused inappropriately. 5) Hardware resources - disk I/O, memory, or CPU constraints. I'd start by checking query execution plans and table growth rates."

Scenario 1: Daily Sales Report

Business Need

Store managers need a daily report showing top-selling products by category

Optimized Query

WITH daily_product_sales AS (
    SELECT
        p.category,
        p.product_name,
        SUM(s.quantity) AS total_quantity,
        SUM(s.amount) AS total_revenue,
        RANK() OVER(PARTITION BY p.category ORDER BY SUM(s.amount) DESC) AS category_rank
    FROM sales s
    JOIN products p ON s.product_id = p.product_id
    WHERE s.transaction_date = CURRENT_DATE - INTERVAL '1 day'
        AND s.store_id = 101 -- Specific store
    GROUP BY p.category, p.product_name
)
SELECT category, product_name, total_quantity, total_revenue
FROM daily_product_sales
WHERE category_rank <= 5 -- Top 5 per category
ORDER BY category, category_rank;

Key Optimizations

✅ Filters on transaction_date early (indexed column)
✅ Uses window function to avoid multiple queries
✅ CTE makes query readable and maintainable
✅ WHERE clause on window function result (filters after ranking)

Scenario 2: Inventory Reorder Alert

Business Need

Identify products that are selling faster than usual and may need reordering
WITH product_velocity AS (
    SELECT product_id, -- Last 7 days average
        AVG(CASE WHEN transaction_date >= CURRENT_DATE - 7 THEN quantity END) AS recent_avg_quantity, -- Last 30 days average
        AVG(CASE WHEN transaction_date >= CURRENT_DATE - 30 THEN quantity END) AS baseline_avg_quantity
    FROM sales
    WHERE transaction_date >= CURRENT_DATE - 30
    GROUP BY product_id
)
SELECT
    p.product_name,
    p.category,
    pv.recent_avg_quantity,
    pv.baseline_avg_quantity,
    ROUND((pv.recent_avg_quantity - pv.baseline_avg_quantity) / pv.baseline_avg_quantity * 100, 2) AS percent_change,
    inv.current_stock
FROM product_velocity pv
JOIN products p ON pv.product_id = p.product_id
JOIN inventory inv ON p.product_id = inv.product_id
WHERE pv.recent_avg_quantity > pv.baseline_avg_quantity * 1.3 -- 30% increase
    AND inv.current_stock < pv.recent_avg_quantity * 7 -- Less than week supply
ORDER BY percent_change DESC;

Scenario 3: Customer Segmentation

Business Need

Identify VIP customers for targeted marketing
WITH customer_metrics AS (
    SELECT
        customer_id,
        COUNT(DISTINCT transaction_date) AS visit_frequency,
        SUM(amount) AS total_spent,
        AVG(amount) AS avg_transaction_value,
        MAX(transaction_date) AS last_visit,
        DATEDIFF(CURRENT_DATE, MAX(transaction_date)) AS days_since_visit
    FROM sales
    WHERE transaction_date >= CURRENT_DATE - INTERVAL '90 days'
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    c.customer_name,
    cm.visit_frequency,
    cm.total_spent,
    cm.avg_transaction_value,
    cm.days_since_visit,
    CASE
        WHEN cm.total_spent > 1000 AND cm.visit_frequency > 10 THEN 'VIP'
        WHEN cm.total_spent > 500 OR cm.visit_frequency > 5 THEN 'Regular'
        WHEN cm.days_since_visit > 30 THEN 'At Risk'
        ELSE 'Casual'
    END AS customer_segment
FROM customer_metrics cm
JOIN customers c ON cm.customer_id = c.customer_id
ORDER BY cm.total_spent DESC;

Question 1: Explain ACID Properties

Show Answer
Answer:

A - Atomicity

Transaction is all-or-nothing. Either all operations succeed or all fail.
Example: Transferring money between accounts - both debit and credit must happen, or neither.

C - Consistency: Database moves from one valid state to another. All rules/constraints are maintained.
Example: Stock levels can't go negative; foreign keys must reference existing records.

I - Isolation: Concurrent transactions don't interfere with each other.
Example: Two customers buying the last item simultaneously - only one succeeds.

D - Durability: Once committed, changes persist even after system failure.
Example: If payment is confirmed, it stays confirmed even if server crashes.

Retail Context

"In our sales system, when a customer completes checkout, we need atomicity to ensure inventory is decremented AND payment is recorded together. Isolation prevents two customers from buying the last item. Durability ensures sales data isn't lost if systems crash during peak hours."

Question 2: Difference Between WHERE and HAVING

Show Answer

WHERE Clause

  • Filters BEFORE grouping
  • Works on individual rows
  • Cannot use aggregate functions
  • Executes first
SELECT category, SUM(amount)
FROM sales
WHERE transaction_date = '2024-01-15'
GROUP BY category;

HAVING Clause

  • Filters AFTER grouping
  • Works on groups
  • Can use aggregate functions
  • Executes after GROUP BY
SELECT category, SUM(amount)
FROM sales
GROUP BY category
HAVING SUM(amount) > 1000;

Combined Example

SELECT category, SUM(amount) AS total
FROM sales
WHERE transaction_date >= '2024-01-01' -- Filter rows first
GROUP BY category
HAVING SUM(amount) > 5000; -- Filter groups second

Question 6: SQL Scenario - Find Second Highest Salary

Show Answer
Multiple Approaches: 
-- Approach 1: Using LIMIT with OFFSET
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

-- Approach 2: Using Subquery
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (
    SELECT MAX(salary)
    FROM employees
);

-- Approach 3: Using Window Function (Most Flexible)
WITH ranked_salaries AS (
    SELECT salary, DENSE_RANK() OVER(ORDER BY salary DESC) AS salary_rank
    FROM employees
)
SELECT salary
FROM ranked_salaries
WHERE salary_rank = 2;

Why DENSE_RANK vs RANK?

• If two people have highest salary ($100K), RANK gives both rank 1, next is rank 3
• DENSE_RANK gives both rank 1, next is rank 2 (what we want for "second highest")
• Window function approach easily extends to "Nth highest"

Question 7: Explain Query Execution Order

Show Answer
SELECT category, SUM(amount) AS total -- 5. Finally select columns
FROM sales -- 1. Start with this table
WHERE transaction_date = '2024-01-15' -- 2. Filter rows
GROUP BY category -- 3. Group filtered rows
HAVING SUM(amount) > 1000 -- 4. Filter groups
ORDER BY total DESC -- 6. Sort results
LIMIT 10; -- 7. Limit output

Actual Execution Order

1. FROM - Identify source tables
2. WHERE - Filter individual rows
3. GROUP BY - Create groups
4. HAVING - Filter groups
5. SELECT - Choose columns
6. ORDER BY - Sort results
7. LIMIT - Restrict rows returned

Common Mistake

You can't use a SELECT alias in WHERE because WHERE executes before SELECT!
-- This FAILS ❌
SELECT amount * quantity AS total
FROM sales
WHERE total > 100; -- total doesn't exist yet!

-- This WORKS ✅
SELECT amount * quantity AS total
FROM sales
WHERE amount * quantity > 100;

Question 9: How Would You Approach a Data Quality Issue?

Show Answer
Systematic Approach:

1. Identify & Quantify

-- Find NULL values
SELECT
    COUNT(*) AS total_rows,
    COUNT(customer_id) AS non_null_customers,
    COUNT(*) - COUNT(customer_id) AS null_customers,
    ROUND((COUNT(*) - COUNT(customer_id)) * 100.0 / COUNT(*), 2) AS null_percentage
FROM sales;
2. Investigate Root Cause:
• When did it start? (trend analysis)
• Which source system?
• Specific stores/products/time periods affected?
3. Assess Impact:
• How many reports affected?
• Which stakeholders impacted?
• Financial impact?
4. Implement Fix:
• Short-term: Data cleanup, filtering bad records
• Long-term: Fix source system, add validation rules
5. Prevent Recurrence:
• Add data quality checks
• Implement monitoring/alerts
• Document in runbook

Retail Example

"If I noticed sales transactions with negative quantities, I'd first query to understand the scale - is it 10 rows or 10,000? I'd check when it started and if it's isolated to specific stores or POS systems. I'd review with the team whether negative quantities are valid (returns/refunds) or data errors. Then I'd work with the source system team to fix the root cause while implementing validation rules to flag future occurrences. I'd also add automated tests to catch this in our data pipeline before it reaches production reports."
